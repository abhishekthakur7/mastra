# Subscription runtime capabilities for Mastra Studio

This document consolidates the repository inspection and the Claude/Codex runtime reviews for the requested local, single-user Mastra Studio surface. The target is the complete registered-agent, configured-tool, and workflow experience. Claude Code is the first runtime; Codex App Server is the second.

The implementation should describe capabilities by evidence level and runtime version. A vendor loop is not categorically excluded, and a vendor feature is not automatically equivalent to a Mastra contract. Each adapter must expose verified, adapter-dependent, and pending capabilities instead of silently dropping behavior.

This is a research inventory, not permission to run with missing dependencies. [SUBSCRIPTION-RUNTIME-RELIABILITY.md](SUBSCRIPTION-RUNTIME-RELIABILITY.md) defines the product behavior for every missing mapping. A required pending/untested capability blocks the affected operation until validated. Predictably blocking an unsupported configuration improves reliability but does not complete the user's requested scope; the gap remains a release blocker.

> **Host-contract review — 2026-09-14.** The statements below were rechecked against the current core implementation, not inferred from the prior runtime research. In particular, normal title and scorer dispatch are best-effort asynchronous work today; dynamic configuration is resolved at runtime; and workflow snapshots are deliberately created before the engine's start gate. A subscription adapter must preserve those default semantics unless an explicitly selected stricter policy changes them.

## Mastra execution seam

The concrete host seam is `Agent.#execute` in `packages/core/src/agent/agent.ts` around line 7230. It resolves model and instructions, request context, memory, workspace/browser, tools, tracing, run IDs, approvals, abort signals, and callbacks, then builds `createPrepareStreamWorkflow`.

`packages/core/src/agent/workflows/prepare-stream/schema.ts` defines `AgentCapabilities` with model/memory access, `convertTools`, input processor execution, `executeOnFinish`, input/output/error processor resolution, and `llm`. `map-results-step.ts` assembles per-run loop options containing tools, request context, actor, thread/resource IDs, `stopWhen`, `maxSteps`, structured output, processors, callbacks, and processor state. It parks closure/class instances under `LOOP_OPTIONS_KEY` in a per-run scope. `stream-step.ts` currently invokes `capabilities.llm.stream()`.

The preferred seam is to generalize the final capability from model-only streaming to a runtime/turn runner, or add an external-runtime stream step adjacent to the existing one. Keep Mastra preparation and finalization; translate vendor events into Mastra stream chunks and invoke only the callbacks the vendor can support. This preserves common route and workflow behavior while making parity explicit.

A direct Agent subclass that overrides `stream()` and immediately calls a vendor SDK bypasses the preparation path. It consequently misses automatic memory, workspace/skill context, tool wrapping, processors, tracing, approval, and finish persistence. This is an observed limitation of the current SDK wrappers, not a conclusion that a properly placed runtime adapter cannot support those behaviors.

`packages/core/src/workflows/entry-executors/run-agent-entry.ts` calls `agent.stream()` and consumes its stream/result. This is why the same adapter can serve ordinary registered agents and `createStepFromAgent` workflow steps. Mastra should remain authoritative for workflow graph execution, scheduling, retries, snapshots, cancellation, persistence, time travel, and resume.

The prepare-stream seam is necessary but not automatically universal. The following execution paths require explicit tested coverage; none is automatically excluded from the requested agent scope.

| Ordinary `generate()` / `stream()` | `Agent.#execute` → prepare-stream → `stream-step.ts` | Primary adapter seam |

## Processor contracts

`packages/core/src/processors/runner.ts` exposes these phases:

- `runInputProcessors` (around line 1229): initial message-list processing before the loop; may rewrite input or trigger a `TripWire` abort/retry.
- `runProcessInputStep` (around line 1471): per-loop input step with messages/system messages/state, model, tools, tool choice, active tools, provider options, model settings, and structured-output data; may rewrite step inputs or retry/abort.
- `runProcessLLMRequest` (around line 1774): immediately before a provider request; may rewrite the provider prompt/request or return a cached response without calling the model.
- `runProcessLLMResponse` (around line 1898): after provider response; may inspect or transform the returned response.
- `runProcessOutputStep` (around line 2027): after a model response and before tool execution/next step; may mutate messages or trigger retry/abort.
- `runProcessToolResult` (around line 2246): after tool execution and before result append/next request; may redact or transform the result or trigger retry/abort.
- `runProcessAPIError` (around line 2445): provider/request failure processing, including classification, retry, or abort.
- `runOutputProcessorsForStream` (around line 1126): per output chunk; may filter or mutate visible stream data.
- `runOutputProcessors` (around line 695): final cumulative output processing.

The prepare-stream finalization path calls `capabilities.executeOnFinish` in `map-results-step.ts`. A vendor final text event is not a substitute for its host persistence, tracing, and callback work. Its current semantics are deliberately mixed: `map-results-step.ts` catches and logs `executeOnFinish` failures before invoking user `onFinish`; title generation is fire-and-forget (or registered with `waitUntil`); and live scorer hooks are dispatched without awaiting their result. The adapter must preserve that normal outcome behavior; any normalized persisted/retryable diagnostic is future adapter contract. A strict "finalization must complete before success" policy would be a deliberate new product option, not parity.

An adapter can usually run initial input processing before a vendor turn and final output processing afterward. Dynamic processors and `prepareStep` are existing runtime callbacks: resolve them at their normal Mastra phase, then validate the resulting external operation immediately before its vendor/tool boundary. Do not impose a new mandatory declaration format on arbitrary user callbacks in the first version, and do not claim that admission prevents earlier local work such as memory-thread creation. Other per-step, per-request, and error phases need lifecycle-specific callbacks or host orchestration. Neither runtime has been live-tested against these Mastra phases.

## Tool, approval, and memory contracts

`packages/core/src/tools/tool.ts` validates tool input, request context, resume data, suspend data, and output. `packages/core/src/tools/tool-builder/builder.ts` (`createExecute` around line 578 and `build` around line 976) injects Mastra, memory, request context, actor, workspace, browser, tracing/observability, abort signal, writer, suspend, resume data, and nested agent/workflow context.

`packages/core/src/loop/workflows/agentic-execution/tool-call-step.ts` evaluates global and per-tool approval, emits `tool-call-approval`, flushes metadata before suspension, resumes with an explicit decision, and distinguishes approval from ordinary suspension. Nested `agent-*` and `workflow-*` calls carry delegated run IDs and have special resume paths.

A bare MCP `tools/call` does not reproduce all of this. A bridge must preserve exact input/output schemas, request context, actor/workspace, stable call IDs, cancellation, observation, approval, suspend/resume, and nested execution. A `CoreTool.execute()` call by itself also cannot run `processToolResult`: that processor requires the active `MessageList`, loop steps, processor state, call IDs, and mutations. The adapter must own and test that normalized host-loop state. Client/browser tools also require a bidirectional follow-up request from Studio; an adapter cannot silently treat them as ordinary one-shot tools.

Mastra memory has separate transcript/history, working-memory, semantic recall, and observational-memory behavior. Input processors inject memory context; output processors persist messages/observations. A vendor transcript or compaction feature is not automatically Mastra memory. The adapter must choose where each memory source is authoritative and explicitly inject summaries/recall when using vendor-native history.

## Claude Code runtime

### Authentication and process

The recommended first route is one unmodified local `claude` binary process per Studio session. Let Claude Code own its subscription login, keychain/configuration, and refresh behavior. Do not add a Studio Claude login, copy credentials, set `ANTHROPIC_API_KEY`, or route credentials through Mastra.

The documented CLI flags include `-p`, stream JSON input/output, partial messages, hook events, permissions, MCP config, session/resume/fork, JSON schema, tool availability, and dynamic agents. `--max-turns` is treated as a hidden, version-bound switch only when observed in the selected installed executable/SDK invocation; the original T03 evidence saw it absent from Claude `2.1.270` help and present in SDK argv. The host ledger records each admitted fixture reservation and refuses replay after an ambiguous dispatch; it does not impose an application-wide Claude-call quota. The five-scenario T04 plan is a bounded workflow definition, not a global usage limit, and host-validates the per-child integer 1–16 before command construction. The local help says `--bare` skips keychain reads as well as extensions; the strict profile therefore rejects it while retaining vendor authentication through the real macOS `HOME` and unset `CLAUDE_CONFIG_DIR`. See [Claude CLI usage](https://code.claude.com/docs/en/cli-usage).

Headless mode normally loads user/project hooks and MCP configuration without the usual interactive workspace-trust/MCP prompts. The tested baseline is `--safe-mode --tools "" --strict-mcp-config --mcp-config <generated> --setting-sources ""` for the effective Mastra MCP catalog, with explicit owned `cwd`/`TMPDIR`; custom plugins, hooks, skills, and commands are disabled and rejected as inputs. `--restricted` is not used as a substitute for the validated safe-mode profile. See [Claude headless execution](https://code.claude.com/docs/en/headless).

The current executable's strings include `control_request`, `control_response`, `control_cancel_request`, `can_use_tool`, `hook_callback`, permission mode, MCP status/reconnect/call, skill reload, and user-dialog terms. This supports a bidirectional control hypothesis, but strings are not a public wire contract. The first probe must capture fixtures from the installed version and fail clearly on unknown frames.

### Streaming, tools, and permissions

Use stream JSON for ordinary events and handle control frames in both directions. The engine should normalize assistant deltas, thinking, tool calls/results, hook events, permission requests, user dialogs, subagent text, task notifications, final/structured result, errors, and compaction.

Claude built-in tools run inside the process. Distinguish availability from approval: `--allowedTools` auto-approves matching tools and is not a whitelist. Use explicit tool/MCP availability controls as well as permission rules. The current control terms suggest host approval via `can_use_tool`; this is pending a live control exchange. The documented `--permission-prompt-tool` is a possible noninteractive path but needs its own contract test.

For Mastra tools, the default should be a scoped external local MCP bridge generated from the effective resolved Mastra tool catalog, including the agent's configured sources and any permitted memory, toolset, workflow, workspace, skill, browser, client, delegation, and processor-loaded tools. Apply the resolved `activeTools` policy at dispatch as well as catalog publication. Static per-process MCP configuration is the initial path; dynamic MCP replacement/status/reconnect should be enabled only after a versioned fixture works. Native Claude built-ins, project plugins, native skills, and native subagents are opt-in capabilities and must not silently expand or replace the Mastra-managed catalog.

### Functions and hooks

Claude's documented SDK hooks can allow/block, defer, modify tool input, replace tool output, add context, stop/continue, and request approval; command, HTTP, prompt, agent, and MCP-tool hook transports are documented. The CLI stream exposes hook events, but `--include-hook-events` alone does not turn a Mastra JavaScript function into a callback. A local HTTP hook relay is the safer first functions path; a direct `hook_callback` control bridge is a version-coupled experiment using the unmodified binary.

The adapter must keep Mastra processor ordering authoritative. Native Claude hook results can enforce tool policy or feed context, but they do not automatically reproduce Mastra input-step, LLM-request, output-step, tool-result, or finalization payloads.

Matching Claude hooks may execute concurrently with nondeterministic completion order. Register one host relay per relevant event to dispatch Mastra's ordered processor chain; do not register each processor as an independent native hook. SDK function callbacks are documented, but the corresponding direct CLI control wire is not a public stability guarantee. HTTP/command hook relays are the first documented transport candidate; direct `hook_callback` remains a version-tested experiment. See [Claude hooks](https://code.claude.com/docs/en/agent-sdk/hooks).

### Native skills, commands, subagents, and workflows

Normal CLI settings can load `.claude/skills`, `.claude/commands`, plugins, `CLAUDE.md`, auto-memory, and native agents. Preserve explicitly selected features rather than blanket-disabling extensions. Define controlled settings sources and enforce tool permissions through skills, hooks, and delegated agents; do not simply inherit every user/project extension. `--bare` is unsuitable for the researched subscription route because it also bypasses subscription credential lookup. Native skills and commands can express useful procedures alongside Mastra workflow graphs.

Native subagents and dynamic `--agents` definitions can coexist with registered Mastra agents. Parse `parent_tool_use_id`, task notifications, and forwarded subagent text when available. Generate validated dynamic definitions only at process start unless live control supports mutation.

Mastra workflows remain the durable orchestrator. A workflow step may call the Claude runtime, store the Claude session ID, receive normalized events, and resume the same session/process or a documented `--resume` path. Native tasks/subagents can implement a focused step but do not replace Mastra typed step schemas, state, retries, suspension, or time travel.

### Sessions, memory, structured output, and limits

Use explicit Studio UUIDs and persist Claude session IDs. Prefer `--session-id`, `--resume`, and `--fork-session`; avoid implicit directory-scoped `--continue`. Keep three identities separate: Claude transcript, Claude native config/memory, and Mastra memory/workflow/storage. Native auto-memory/CLAUDE.md is not Mastra memory.

`--json-schema` produces a final structured value; it is not token-level JSON streaming. Parse the final value and validate it using Mastra's output schema. A follow-up documentation check corrected the earlier checkpoint assessment: Claude documents CLI rewind with `claude -p --resume <session-id> --rewind-files <checkpoint-uuid>`. Help output is not exhaustive. Treat this as documented native functionality requiring a versioned round-trip test, not an absent CLI feature. File checkpoints have coverage limits and do not undo arbitrary external tool effects or substitute for Mastra workflow state. See [Claude checkpointing](https://code.claude.com/docs/en/checkpointing) and [file checkpointing integration](https://code.claude.com/docs/en/agent-sdk/file-checkpointing).

Task tools and progress notifications can feed Studio progress UI. Cost fields are estimates and should not be shown as subscription invoices. OpenTelemetry must remain opt-in and visible.

## Codex App Server runtime

### Transport, account, and protocol

The local CLI exposes `app-server`, marked experimental, with default `stdio://` plus other transports. The official lifecycle is initialize → thread/start → turn/start. Generated protocol bindings are version-specific: local experimental schema includes dynamic tools and broader runtime controls, while stable generated schema includes stable turn output schema but not dynamic tools. Evidence: local help and generated schemas; no live app-server handshake was executed. See [App Server protocol](https://learn.chatgpt.com/docs/app-server).

The app-server supports subscription account login methods, threads/history/fork/archive/delete, streamed turn/item/hook/tool/MCP/account/usage notifications, interruption, steering, compaction, structured output, command/file approvals, MCP elicitation, and dynamic tools according to the inspected 0.154.0 schemas. Treat dynamic tools, collaboration, plugins, and other experimental fields as version-negotiated. The feature registry is a maturity signal, not a complete app-server contract; for example, schemas may contain steering/collaboration fields while CLI feature flags differ.

Use managed browser/device-code authentication. The inspected schema labels external `chatgptAuthTokens` internal-only, so that route must not become Studio's integration. See [App Server account flows](https://learn.chatgpt.com/docs/app-server).

### Hooks and processor mapping

Current reports identify Codex hook surfaces including `UserPromptSubmit`, `SessionStart`, `PreToolUse`, `PostToolUse`, `PermissionRequest`, `Stop`, `SubagentStop`, `PreCompact`, and `PostCompact`. The repository/schema report also notes that prompt and agent hook handler variants are parsed but currently skipped by the official Hooks page; do not infer active support from types alone. Evidence is official hook documentation plus local schema inspection, not live execution. See [Codex Hooks](https://learn.chatgpt.com/docs/hooks).

Codex hook configuration merges across layers; a generated Studio config does not by itself suppress inherited user/project hooks. Validate the effective configuration and isolation policy, including whether `allow_managed_hooks_only` applies to the chosen deployment. Separately prove native tool availability restrictions: approval prompts and hook coverage do not constitute a hard-disable guarantee.

`PreToolUse` receives tool name, call ID, and JSON input and can deny, add model-visible context, or rewrite input. This maps to tool-policy cases. `PostToolUse` provides model-visible corrective feedback, but does not itself mutate Mastra storage. The inspected hook contract reports hook failures, missing tools/servers, and unsupported fields as failed events while allowing the turn to continue; hosted WebSearch and other special paths are also outside its normal Pre/Post coverage. Hooks therefore cannot be the sole configured-tool guardrail. The host bridge must gate the effective Mastra tool catalog before execution and process/persist host-tool results before sending them to Codex. No post-execution processor, vendor or Mastra, inherently undoes an external side effect.

Codex emits agent-message deltas, plans, reasoning summaries, item lifecycle events, and completed items. The adapter can filter Studio display output, but arbitrary native per-token replacement is not documented. Mastra output-step guardrails therefore need an adapter event barrier or a host wrapper.

`Stop`/`SubagentStop` can request bounded continuation by injecting a new continuation reason; this is not identical to Mastra `isTaskComplete` scoring. `PreCompact`, `PostCompact`, and compact `SessionStart` can restore summaries/context at the compaction boundary; they are not replacements for Mastra semantic, working, or observational memory.

### Dynamic tools, MCP, skills, commands, and subagents

Experimental `dynamicTools` and `item/tool/call` provide a direct host callback path in the inspected 0.154.0 schema. Prefer this when `initialize` capability negotiation confirms it; retain MCP for shared tools, long-lived services, OAuth, and workflow endpoints. Because the field is experimental, keep a fallback for versions without it.

Choose an equivalent tool bridge before execution; do not switch transports after a call or approval has begun. Native skills can declare environment-variable and MCP dependencies. Resolve those dependencies and permissions explicitly; enabling a skill must not silently enable external tools or credential sources. See [Codex skills](https://learn.chatgpt.com/docs/build-skills).

The default dynamic tool set should be the effective resolved Mastra catalog, filtered by active-tool and approval policy. Native Codex built-ins, skills, plugins, and subagents must be explicit opt-ins; native capabilities must not implicitly expose every Mastra tool or bypass Mastra approval. Skills are reusable instructions/configuration. CLI slash commands and custom prompts are CLI/IDE UX, not a guaranteed app-server RPC; the official custom-prompt page directs reusable behavior toward skills. See [Codex skills](https://learn.chatgpt.com/docs/build-skills) and [custom prompts](https://learn.chatgpt.com/docs/custom-prompts).

Codex collaboration/subagent items can coexist with Mastra agents, but the adapter must choose an ownership model: represent provider-native child threads as provider-internal events, or map them to Mastra child runs with durable IDs. Do not merge the two identities implicitly.

### Sessions, memory, workflows, and approvals

Persist Mastra thread ID ↔ Codex thread ID, cwd, model, provider version, and negotiated capabilities. Let Codex own native rollout history when selected, while treating Mastra memory as an explicit independent feature. Inject recall/working-memory summaries through the initial turn, prompt context, dynamic tool, or hook; do not claim compaction is equivalent to Mastra memory.

Map Codex request, thread, turn, item, and approval IDs to Mastra run/tool IDs. Keep command/file approval, MCP elicitation, and Mastra tool approval distinct in the ledger. A suspended Mastra tool may resume the same Codex thread/turn only after the corresponding durable mapping and host approval are restored.

Expose Mastra workflow start/status/suspend/resume/result as dynamic tools or MCP. A full Codex turn can supply an ordinary Mastra agent step's result. Making recovery of an in-flight step durable additionally requires explicit checkpoints, resume IDs, and side-effect accounting.

## Functions versus MCP bridge architecture

The two transports serve different contracts:

- **MCP bridge:** schema-first, process-boundary-safe, reusable by CLI/App Server, appropriate for selected configured Mastra tools, shared services, and workflows. It requires lifecycle, list-change, reconnect, error, approval, and suspend/resume handling.
- **Direct host callbacks:** expose explicit request/response handling for approval, permission, hook decisions, tool execution, and client tools, with version-specific protocol requirements. Claude's `hook_callback` is described in SDK types and observed in executable strings/control terms; Codex `dynamicTools` is present in experimental 0.154.0 schema. Neither path is live-tested here; no latency comparison has been measured.
- **Local HTTP hook relay:** useful for Claude command/HTTP hooks while keeping the CLI unmodified. It should be treated as an event/decision relay, not as a replacement for all Mastra processors.

Start Claude with static external MCP plus a normalized stream/control parser. Add direct hook/control callbacks only after fixture tests. Start Codex with stdio app-server, `initialize` capability negotiation, and dynamic tools only when the installed schema advertises them; MCP remains the fallback.

## Implementation order and remaining decisions

The authoritative sequence is [SUBSCRIPTION-RUNTIME-PLAN.md](SUBSCRIPTION-RUNTIME-PLAN.md): capability/spike tests, the common runtime seam, Claude backend and host bridge, state/workflow compatibility, Studio integration, then Codex App Server.

Hooks, configured tools, client-tool callbacks, selected skills/commands, and subagent behavior belong in the initial compatibility work. Their inclusion must follow verified mappings rather than being deferred solely because a runtime owns the model loop. The requested agent/tool/workflow coverage remains the release target.

Keep Claude authentication in its own CLI login flow. Codex's documented App Server account flow can support a Studio connection action without Studio handling tokens. Shared transport code should not implement private provider authentication.

Pending experiments include complete processor ordering, dynamic capability updates after resume, documented native checkpoint/rewind behavior on the installed version, recovery of pending tool requests after process loss, and consistent usage/structured results. Pending does not mean safe to execute. Block configurations that depend on an unvalidated contract, retain the gap in the release checklist, and record the failure precisely before deciding whether an alternative implementation or an explicit scope decision is needed.
